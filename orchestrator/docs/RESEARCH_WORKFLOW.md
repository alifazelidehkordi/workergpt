# نقشهٔ توسعه و اجرای پژوهش کینتسوگی

## هدف

این سند نقشهٔ پایدارسازی WorkerGPT Orchestrator و تکمیل ۶۰ پروندهٔ باقی‌ماندهٔ پژوهش کینتسوگی است. کار سنگین پژوهش، نقد و بازنویسی به ChatGPT وب سپرده می‌شود؛ Orchestrator مسئول تقسیم کار، ذخیرهٔ خروجی، کنترل کیفیت، checkpoint و ادامهٔ دقیق فرایند است.

## چرخهٔ هر پرونده

هر پرونده به شش بخش محدود تقسیم می‌شود:

1. تعریف سازه و مرزبندی مفهومی؛
2. نظریه‌های حامی و رقیب؛
3. مکانیسم‌ها، میانجی‌ها و تعدیل‌گرها؛
4. مطالعات تجربی و جدول شواهد؛
5. محدودیت‌ها، شواهد منفی، ایمنی و شرایط مرزی؛
6. قانون عملیاتی و اصول قابل‌آزمون کینتسوگی.

ابتدا Planner یک برنامهٔ ساختاریافته با شش شناسهٔ دقیق، پرسش‌ها، عبارت‌های جست‌وجو و موارد حذف‌شدنی می‌سازد. این برنامه یک‌بار ذخیره و با هش محافظت می‌شود. سپس برای هر بخش این چرخه اجرا می‌شود:

`Researcher → اعتبارسنجی محلی → ذخیرهٔ draft → Critic مستقل و فقط ممیزی → pass و ذخیرهٔ approved، یا revise و Researcher تازه`

پس از تکمیل شش بخش:

`ادغام قطعی محلی → Critic نهایی پرونده → اعتبارسنجی ساختاری → پشتیبان‌گیری → جایگزینی فایل → همگام‌سازی ایندکس و گزارش`

## قواعد کیفیت

- خروجی پژوهش و نقد در بلوک کد Markdown برگردانده می‌شود تا نشانه‌های Markdown هنگام رندر رابط وب حذف نشوند.
- هر بخش باید منبع علمی قابل‌ردیابی داشته باشد؛ DOI، PMID، PMCID یا صفحهٔ رسمی ناشر بر وبلاگ و محتوای عمومی مقدم است.
- نظریه، همبستگی، شاهد علّی و استنباط طراحی باید جدا بمانند.
- شواهد منفی، ناهمگونی، محدودیت تعمیم و خطرهای کاربرد حذف نمی‌شوند.
- هیچ فایل اصلی پیش از قبولی Critic نهایی و validator محلی بازنویسی نمی‌شود.
- frontmatter، wikilink و calloutهای Obsidian حفظ می‌شوند.

## ادامه‌پذیری

- وضعیت هر بخش جداگانه در `projects/<id>/research_workflow.json` ذخیره می‌شود.
- draft و نسخهٔ نقدشده در `projects/<id>/research_artifacts/<topic>/<section>/` باقی می‌مانند.
- پاسخ ساختاریافتهٔ هر Critic در `critic_review.json` نگه داشته می‌شود. Critic متن را بازنویسی نمی‌کند؛ فقط `verdict`، issueهای ساختاریافته و source checkها را برمی‌گرداند. فقط `pass` بدون issue مسدودکننده/major، همان draft پژوهشگر را approved می‌کند.
- هر `revise` یا شکست اعتبارسنجی پیش از Critic، تلاش قبلی را با فایل‌ها و هش‌هایش در `revisions/section-attempt-N/` غیرقابل‌تغییر نگه می‌دارد، بازخورد را به یک فراخوانی تازهٔ Researcher می‌دهد و سپس Critic تازه اجرا می‌شود. سقف این چرخه `--max-section-revisions` است.
- اعتبارسنجی پیش از Critic تیتر دقیق، طول محدود، ارجاع `[n]`، لینک واقعی `https`، جدول بخش شواهد و نبود tokenهای داخلی/UI مانند `contentReference` و `oaicite` را کنترل می‌کند.
- هش محتوای منبع، draft و approved ثبت می‌شود؛ تغییر بیرونی به‌جای بازنویسی خاموش، workflow را متوقف می‌کند.
- شکست مرورگر یا سقف مصرف فقط همان مرحله را متوقف می‌کند؛ اجرای بعدی از نخستین مرحلهٔ ناقص ادامه می‌یابد.
- verdict نهایی `revise` در صورت داشتن issue با `section_ids` معتبر، حداکثر به تعداد `--max-revisions` فقط همان بخش‌ها را دوباره پژوهش و نقد می‌کند. نقد‌های حل‌نشده برای بررسی انسانی نگه داشته می‌شوند.
- پیش از جایگزینی فایل اصلی، commit journal و نسخهٔ `original.md` ثبت می‌شود؛ اگر فرایند پس از نوشتن فایل قطع شود، اجرای بعدی commit را از روی هش بازیابی و ایندکس را دوباره همگام می‌کند.
- یک پروفایل مرورگر به‌صورت ترتیبی استفاده می‌شود تا خرابی پروفایل و تداخل پاسخ‌ها رخ ندهد.

## فرمان‌ها

```bash
python -m orchestrator workflow init kintsugi --vault /path/to/vault
python -m orchestrator workflow status kintsugi
python -m orchestrator --real workflow run kintsugi --topic KSR-10
```

در init تعداد مورد انتظار به‌طور پیش‌فرض ۷۰ شناسهٔ یکتا است. برای vault آزمایشی می‌توان `--expected-topics N` داد یا با مقدار صفر فقط کنترل تعداد را غیرفعال کرد.

## ترتیب اجرا

1. تکمیل و ممیزی KSR-10 به‌عنوان پایلوت؛
2. تکمیل موج دوم: KSR-11 و KSR-13 تا KSR-25؛
3. بازبینی کیفیت موج دوم و اصلاح promptها؛
4. اجرای موج‌های سوم تا پنجم؛
5. ممیزی نهایی ۷۰ پرونده، ایندکس و گزارش جامع.

## معیار پایان کل پروژه

- ۷۰ فایل موجود و بدون placeholder؛
- همهٔ پرونده‌ها دارای شش بخش، منابع، جدول شواهد، نقد و قانون عملی؛
- وضعیت frontmatter، ایندکس و گزارش یکسان؛
- همهٔ خروجی‌ها دارای provenance و artifact قابل‌بازبینی؛
- تست‌های Orchestrator و validator محلی سبز؛
- هیچ checkpoint ناقص یا مرحلهٔ `in_progress` باقی نمانده باشد.
